# DEC-016 · 聊天式入口 + 并行审查

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-002、DEC-014、DEC-015

## 背景

第一版面板是「选任务 → 点运行」的控制台，任务必须提前写进 `tasks/<id>/`。
实际使用时想要的是：**像聊天一样把需求丢进去，然后看着工作流自己跑，
直到代码审核通过**。这带来两个具体问题：

1. **自由输入没有任务定义**：没有 `task.md`、没有验收项、没有测试用例。
   原来的验收器写死了 `class TTLCache` + `get/put`，会直接判自由输入的代码不合格。
2. **「并行执行」此前没有落地**：作业把它列在推荐项里，而我们只做了顺序循环。

## 可选项

1. 让面板直接 import 编排器，在 GUI 线程里跑 —— 界面会卡死，且无法真正「停止」。
2. 只做前端假流式（把预先跑完的输出慢慢打印）—— 不是真并行/真进度，容易露馅。
3. **新增 `--prompt` / `--events` 两个 CLI 能力，面板只做「事件 → 对话」的翻译**（本方案）。
4. 并行方面再引入通用调度框架 —— 为两个审查员引框架，成本远大于收益。

## 决定

### 1. 聊天输入 = 一次性任务

- `workflow.cli run --prompt-file <md>` 把这句话写成 `runs/_prompts/<id>/task.md`
  （`Task.from_prompt`），**不污染 `tasks/`**；
- 没有固定类名时，静态检查退化为**通用检查**：语法、非空、无 `pass/.../NotImplementedError` 占位；
- 如果生成代码里出现了已知任务的类名（如 `TTLCache`），自动复用该任务的测试套件
  （`infer_tests`），于是自由输入同样能享受 25 个用例的机器验收。

### 2. 事件流（`--events`）

编排器新增可选 `event_sink`，在关键点推结构化事件：
`session / code / verification / review / loop / done`。
`--events` 时 CLI 只输出 JSONL，人类可读的排版交给订阅方（面板 / 脚本）。

### 3. 并行审查（`--parallel-review`）

`_run_reviewers()` 把「主审查 + 安全审查」两个 Agent 放进线程池并发执行，
join 后合并：**都通过才算通过**（取交集）、问题取并集（按 problem 去重）、分数取最低。
开关默认关闭，可通过 `--parallel-review` 或 `config.limits.parallel_review` 打开。

### 4. 面板只做翻译

面板用子进程跑 `--cli ... --events`，把每行 JSON 渲染成对话气泡：
代码按行预览、验收证据展开、审查问题逐条列、分支与终态单独成条。
「停止」用 `taskkill /T` 杀掉整棵进程树。

## 理由

- **GUI 不碰编排逻辑**：面板换掉不影响工作流，工作流也能被 CLI / 脚本单独驱动；
- **自由输入的验收不注水**：能复用测试就复用，不能复用就明说「只做了静态检查」，
  面板会把 `tests_from` 显示出来，避免「看起来通过了其实没测」；
- **并行有明确语义**：两个审查员结论取交集，是保守合并，不会因为一个说通过就放行。

## 代价与后果

- 自由输入任务通常没有测试，机器验收只剩静态检查，**结论强度弱于 `tasks/` 里的任务**；
  面板会在验收消息里标注「复用的测试套件」或直接显示 pytest 未执行。
- 并行审查每轮多一次 LLM 调用（成本 ×2），默认关闭以免误开机费。
- 事件流是新增的对外契约：新增阶段时要记得补事件，否则面板上看不到（不影响正确性）。
- 面板与 CLI 通过 JSONL 解耦，字段改名要同时改 `launcher/panel.py::render_event`。

## 复核条件

若自由输入成为主要用法，应引入「按需求生成测试」的第四步（测试 Agent 或模板匹配），
把「没有测试 → 只能静态检查」的强度缺口补上；届时要同步评估生成测试本身的质量与成本。
