# DEC-001 · 技术栈：Python 标准库 + requests，不引入编排框架

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-002、DEC-005、README「架构」

## 背景

作业要求「理解 Workflow 编排、Agent 间通信、状态管理等核心概念」。如果用 LangGraph /
CrewAI 这类框架，20 行就能拼出一个流水线，但编排、通信、状态全部藏在框架内部，
恰恰把要理解的三件事变成了黑盒。另一方面，交付物还得能被评分者直接读懂、直接跑。

## 可选项

1. **LangGraph / CrewAI 等编排框架**：现成的图结构、内置状态、开箱即用的 agent 抽象。
2. **自研轻量实现**：标准库（`dataclasses` / `threading` / `json`）+ `requests`，约 1500 行。
3. **纯脚本**：一个 `main.py` 顺序调用三个函数，不用类、不留状态。

## 决定

选 **方案 2**：不依赖任何编排框架，`requests` 只用于调模型和调 GitHub API；编排器、
消息总线、状态机、DEC 记录器全部手写，每个概念对应一个可读的文件。

## 理由

- 三个核心概念各自有落点：`workflow/orchestrator.py`（编排）、`core/bus.py`（通信）、
  `core/state.py`（状态），评审者能顺着文件读，不用先学框架。
- 依赖只有 `requests`，任何装了 Python 3.9 的机器都能跑，评分时不会卡在装包。
- 自研实现能暴露「为什么需要状态迁移白名单」「为什么要原子落盘」这类真实问题，
  正是作业想让人踩的坑。

## 代价与后果

- 代码量比框架方案多一个数量级，需要自己保证正确性（用测试与静态检查兜底）。
- 没有现成的并发/多分支/人工审核节点；将来要扩展成通用编排平台得重写调度层。
- 换模型、加重试、加流式输出都要自己写，不像框架那样一行配置解决。

## 复核条件

若任务从「单任务线性回路」扩展到「多任务 DAG + 人工审核 + 并行分支」，自研调度器的
维护成本会超过框架收益，届时应重新评估（新开一条 DEC）。
