# DEC-004 · 状态管理：单一状态机 + 原子落盘 + 迁移白名单

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-003、DEC-011

## 背景

工作流的状态包括：当前阶段、已跑几轮、当前代码版本、每轮审查结论、未解决问题、
本轮的验收结果。如果把这些散落在三个 Agent 的实例属性里，一旦某轮崩掉，
既不知道停在哪，也无法续跑；如果阶段可以随便跳（比如审查中途跳回编码），
就会出现「审查意见和代码版本对不上」的幽灵 bug。

## 可选项

1. **各 Agent 自己记状态**：谁用谁存，编排器只做转调。
2. **编排器持有单一 `WorkflowState` dataclass**，每次迁移即落盘 `state.json`。
3. **状态全放内存 + 日志文件**：靠解析日志重建。
4. **上数据库**：SQLite 存状态与消息。

## 决定

选 **方案 2**：
- `WorkflowState` 是唯一真相源，Agent 的入参完全来自 state；
- 阶段迁移走白名单 `Phase.TRANSITIONS`，非法迁移抛 `IllegalTransition`；
- `StateStore.save` 写临时文件后 `os.replace` 原子替换，进程被 kill 也不会留下半个 JSON；
- `--resume` 时从 `state.json` 恢复阶段，并把 `messages.jsonl` 回放进总线。

## 理由

- **可恢复**：落盘是原子的，重启后能精确知道停在哪一步、代码是第几版。
- **可校验**：白名单让「迁移」变成一次显式声明，`REVIEWING → CODING` 这类跳转在
  code review 阶段就会被打回，而不是等到线上出现版本错乱。
- **单一真相源**：Agent 不再有隐式状态，单独跑一个 Agent 也可复现（喂一条消息即可）。
- 相比数据库方案，JSON 文件对作业场景足够，且人可以直接打开看。

## 代价与后果

- 每步都写盘，一次运行约十几次 IO，可忽略；但状态里存了完整代码，
  `state.json` 会有十几 KB。
- 只支持「单写者」：同一 run_id 不能被两个进程同时续跑，否则会互相覆盖。
  作业场景不需要，真要做到得加文件锁。
- 迁移白名单要维护：加阶段就得同时改 `TRANSITIONS`，否则新阶段不可达（这是有意的）。

## 复核条件

出现「同一 run 需要并发续跑」或「状态需要跨机器共享」时，改用带锁/事务的存储。
