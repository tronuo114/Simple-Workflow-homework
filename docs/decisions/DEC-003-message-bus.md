# DEC-003 · Agent 间通信：收件箱式消息总线 + JSONL 全量落盘

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-004、README「消息协议」

## 背景

三个 Agent 之间怎么传话，看起来是实现细节，其实决定了三件事：能不能单独测某个 Agent、
出问题时能不能复盘、加第四个 Agent 时要不要改已有的 Agent。常见做法是编排器直接
`code = coder.run(task)`，简单但把数据格式和调用顺序焊死在调用方。

## 可选项

1. **直接函数调用**：编排器持有 Agent 实例，按名字调方法，返回结构化数据。
2. **收件箱式消息总线**：每个 Agent 一个收件箱，`publish` 投递、`consume` 取用，
   消息落盘 `messages.jsonl`。
3. **HTTP / 进程间通信**：Agent 跑成独立服务，用网络协议通信。
4. **共享状态（blackboard）**：所有 Agent 读写同一块内存/文件。

## 决定

选 **方案 2**：`core/bus.py` 实现线程安全的总线，消息是带 `kind` 的 dataclass，
六种类型（`task` / `code` / `review_request` / `review` / `fix_request` / `status`），
全部按序写入 `runs/<run_id>/messages.jsonl`。

## 理由

- **解耦**：发送方只知道「消息类型 + 载荷」，不知道谁消费、有几个消费者；
  加一个「安全检查 Agent」只需注册收件箱并订阅 `code`。
- **可观测**：消息流水就是完整的执行时间线，报告里的「Agent 通信流水」直接由它生成，
  不用额外埋点。
- **可续跑**：`--resume` 时把 JSONL 回放进总线，历史上下文不丢（DEC-004）。
- **代价可控**：进程内收件箱没有网络开销，也不需要序列化协议版本管理，
  但接口形状与真实消息队列一致，将来换成 MQ 只改总线实现。

## 代价与后果

- 消息体里有完整代码，`messages.jsonl` 体积不小（一次两轮运行约 50 KB）；
  落盘时不做压缩、不截断，优先保证可复盘。
- 载荷没有 schema 校验，字段缺失靠调用方 `.get()` 兜底；接口演进需要自律。
- 广播（`recipient="*"`）会把 `status` 塞进所有收件箱，Agent 必须忽略未知类型。

## 复核条件

当需要跨进程/跨机器拆分 Agent，或需要消息重放与死信队列时，把 `MessageBus` 换成
真实 MQ 实现（接口不变）。
