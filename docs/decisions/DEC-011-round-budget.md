# DEC-011 · 轮次上限 3 轮 + 熔断交出问题清单

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-002、DEC-004

## 背景

「审查不通过就修」是个天然的死循环结构：修复 Agent 可能改不好，审查 Agent 可能提新问题，
工作流就会一直转下去，烧完 token 也没有结论。需要一个明确的预算与退出语义。

## 可选项

1. **不设上限**：直到通过为止。简单，但可能无限循环，且没有收敛保证。
2. **固定 3 轮**（本方案）：达到上限仍未通过则 `REJECTED`，输出遗留问题清单。
3. **按 token/金额预算**：更贴近成本，但需要先有准确用量统计与价格表。
4. **转人工**：超过 N 轮后把状态挂起，等人审。

## 决定

选 **方案 2**：`config/agents.json` 的 `limits.max_rounds = 3`，可通过 `--rounds` 覆盖。
第 3 轮仍未通过时：状态迁移到 `REJECTED`，写一条「达到轮次上限，熔断」的 DEC，
报告中列出全部遗留问题与最后一版代码。

## 理由

- 经验上这类实现题 2 轮足够：第一版通常缺线程安全/惰性删除，修一次就到位；
  到第 3 轮还不过，多半是需求理解分歧（比如「过期条目占容量」的判定口径），
  继续重试解决不了，交给人更快。
- 3 轮的成本上界很清晰：最多 1 次编码 + 3 次审查 + 2 次修复。
- `REJECTED` 不等于「白干」：产物包含最后一版代码、完整问题清单、每轮的 DEC，
  人能直接接着改。

## 代价与后果

- 简单任务本来 1 轮就过，上限设置不影响；复杂任务可能被过早截断，需要手动 `--rounds 5`。
- 不做成本统计，`max_rounds` 是唯一预算旋钮；若接入真实计费，应改成按 token 预算。
- 熔断后的 `REJECTED` 状态是终态，`--resume` 不会继续跑（除非改状态文件）。

## 复核条件

若接入真实计费且单价差异大（如不同 Agent 用不同模型），把预算从「轮次」改为「金额」，
并保留轮次作为第二道防线。
