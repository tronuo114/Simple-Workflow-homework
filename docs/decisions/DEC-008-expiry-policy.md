# DEC-008 · 过期清理策略：惰性删除 + 容量满时优先清理，不启后台线程

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级（TTLCache 实现）
- **关联**：DEC-007、DEC-009

## 背景

题目要求「过期条目不应长期占用容量（惰性删除 + 容量满时优先清理过期）」。
但「不长期占用」是个模糊口径，实现上有三种主动性完全不同的做法，成本和副作用差别很大。

## 可选项

1. **只惰性删除**：`get` 时发现过期才删。实现最省，但一个不再被访问的过期条目会一直占着容量，
   直到被 LRU 淘汰——不符合「不应长期占用」。
2. **惰性删除 + 容量满时优先清理过期**（本方案）：写入时若容量紧张，先按到期队列清一批过期条目，
   仍然满才淘汰 LRU。
3. **后台定时清扫线程**：起一个 daemon 线程每隔 N 秒全量清理。
4. **每次 put 都全量清扫**：正确但 O(n)，违反 REQ-6。

## 决定

选 **方案 2**，并且：
- `get` 命中过期条目时**就地删除**（`del self._data[key]`），而不是只返回 None；
- `put` 新 key 前先调用 `_purge_expired(now)`，把队首所有已到期条目清掉；
- 提供公开的 `purge_expired()`，让调用方可以在空闲时主动巡检（但不是必须）。

## 理由

- 方案 2 同时满足「过期不长期占容量」和「均摊 O(1)」：清理动作的触发点是写入，
  且每次清理的都是队首连续过期段，每个元组一生只被弹出一次。
- **不起线程**：后台线程会带来锁竞争、生命周期管理（谁来 stop）、fork 不安全等问题；
  一个纯计算型缓存不该偷偷占用线程资源，这在服务端是反模式。
- **不全量清扫**：`for key in list(self._data)` 是 O(n)，直接违反验收项 REQ-6，
  而且高频写入时会让 `put` 抖动。
- 保留手动 `purge_expired()`，把「要不要更激进地回收内存」的决定权交给调用方，
  而不是替它决定。

## 代价与后果

- 极端情况下（写入很少、读也很少、TTL 又长）过期条目会在内存里多待一会儿，
  直到下一次写入触发清理或手动 `purge_expired()`。这是有意的权衡：正确性不受影响，
  `get` 永远不会返回过期值。
- `len(cache)` 统计的是「容器里的条目数」，包含尚未被清理的过期条目；
  测试与文档都写明这一点，避免误解为「有效条目数」。
- 需要有到期队列做支撑（DEC-007），否则「优先清理过期」无法 O(1) 完成。

## 复核条件

若场景要求「内存占用是硬约束」或「条目过期必须触发回调」，应引入后台清扫 +
确认清理的变体，并新开 DEC 记录新的取舍。
