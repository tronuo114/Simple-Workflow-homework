# DEC-012 · 可追溯性：messages.jsonl + decisions.jsonl + 自动 REPORT.md

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-003、DEC-004

## 背景

作业要求「每次决策都要留下 DEC 编号」。但只写一堆 Markdown 是静态的：评审者会问
「这次运行到底在第几轮打回、为什么打回、修的代码真的过了测试吗」。
所以必须让**每次运行的决策自动带编号落盘**，而且能和消息、代码版本对上。

## 可选项

1. **只写项目级 DEC 文档**：手写，清晰，但和具体某次运行无关，无法证明流程真的这样跑。
2. **只打日志**：`print` 到控制台，事后无法检索，也留不下来。
3. **项目级 DEC 文档 + 运行级 DEC（自动编号落盘）+ 自动生成 REPORT.md**（本方案）。
4. **上可观测平台**（Langfuse 等）：专业，但引入外部服务，作业场景过重。

## 决定

选 **方案 3**，三层证据链：

1. **项目级** `docs/decisions/DEC-001…015`：架构/选型类决策，编号全局唯一，只追加。
2. **运行级** `runs/<run_id>/decisions.jsonl` + `DECISIONS.md`：编排器在每个关键点
   （进入修复、强制驳回、熔断、落地、续跑）调用 `DecRecorder.record()` 自动编号，
   每条都带背景/可选项/决定/理由/代价。
3. **运行报告** `runs/<run_id>/REPORT.md`：把状态、验收证据、审查记录、DEC 表、
   Agent 通信流水、模型调用统计、最终代码汇总成一页，直接可贴进作业。

另外：
- 编号从已有文件扫描恢复（`_scan_count`），续跑不会重号；
- 索引表每次追加后**整体重建**，避免并发追加导致表头重复；
- `runs/` 目录被 `.gitignore` 忽略，避免把运行产物当源码提交；
  代表性的运行记录另存到 `examples/` 作为证据（去掉 pycache 与 workspace）。

## 理由

- 静态 DEC 文档负责「为什么这样设计」，运行级 DEC 负责「这一次为什么这样做」，
  两者合起来才回答得清楚评审者的问题。
- 自动化是可持续的关键：靠人手写决策记录，三轮之后就没人写了。
- REPORT.md 把散落的 JSONL「翻译」成人能读的表格，降低评审成本。

## 代价与后果

- 每次运行多写三四个文件（约 100 KB 内），IO 可忽略。
- DEC 文案由编排器模板生成，信息量取决于调用点写得多细；
  如果只写「进入修复」而不写问题摘要，记录会退化成流水账——所以调用点都带上下文。
- 运行产物不进仓库，评审者需要看 `examples/` 才有具体证据；这是刻意的取舍
  （避免仓库里堆满每次运行的 JSON）。

## 复核条件

若需要跨运行的趋势分析（通过率、平均轮次），应把 `decisions.jsonl` 汇总到 SQLite
或导出 CSV，而不是继续靠 Markdown 索引。
