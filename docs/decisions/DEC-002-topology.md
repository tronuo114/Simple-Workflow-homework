# DEC-002 · 拓扑：编码 → 审查 → 修复，三个 Agent，不设测试 Agent

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-001、DEC-006、DEC-011

## 背景

题目给定「代码审查流程：编码 → 审查 → 修复，编码 Agent + 审查 Agent + 修复 Agent」。
但真正要定的是三个细节：**谁拥有流程控制权**、**审查不通过时重写还是定点修**、
**测试由谁执行**。这三件事决定工作流能不能收敛。

## 可选项

1. **双 Agent（编码 + 审查）**：审查不通过就让编码 Agent 重写整份代码。
2. **三 Agent（编码 + 审查 + 修复）**，编排器持有状态机：修复 Agent 只针对问题清单定点改。
3. **四 Agent（加测试 Agent）**：由 Agent 写测试、跑测试、报告结果。
4. **Agent 之间直接互调**：审查 Agent 直接调用修复 Agent，无中心编排。

## 决定

选 **方案 2**。编排器（`Orchestrator`）独占状态机与轮次预算，三个 Agent 无状态、
只认消息；测试由**代码**跑（pytest），不交给 Agent。审查不通过走定点修复，
最多 3 轮（DEC-011）。

## 理由

- **重写有回归风险**：让编码 Agent 重写，会把已经通过的部分改坏，且审查意见与代码
  版本无法一一对应；定点修复能把「问题 ID → 改动」对上，下一轮审查可以逐条核对。
- **测试交给 LLM 反而更不可靠**：跑 pytest 是可复现的确定性操作，让 Agent「报告测试结果」
  会引入新的幻觉面（DEC-006）。LLM 应该做它擅长的判断（代码是否有缺陷），
  把确定性的执行交给代码。
- **控制权集中在编排器**：Agent 之间互调会让调用链变成网状，出问题无法定位、无法限流；
  中心编排器是唯一能记账、能熔断、能落盘的地方。

## 代价与后果

- 多一轮模型调用（修复），成本约 +30%。
- 修复 Agent 可能「只改表面」而不动结构性问题；这类问题要么在下一轮被审查抓住，
  要么落到 `REJECTED` 交人工（这本身是可接受的结局，比无限重试好）。
- 三个 Agent 的输出格式必须严格约定（代码块 / JSON），否则编排器无法解析。

## 复核条件

若某类任务的缺陷大多是结构性的（重写比定点修更有效），应为该类任务单独配置
「重写」策略，而不是全局切换。
