# DEC-006 · 机器验收优先于模型判断（自动验收卡口）

- **状态**：已采纳
- **日期**：2026-10-25
- **范围**：项目级
- **关联**：DEC-002、DEC-005、README「验收」

## 背景

审查 Agent 是 LLM：会漏看、会被注释说服、会在「整体看起来不错」时给出 `approved: true`。
如果放行完全由它决定，工作流就可能输出「报告漂亮、测试全红」的代码——
而这套作业的最终验收恰恰是跑测试。

## 可选项

1. **完全信任审查 Agent**：LLM 说通过就通过。
2. **完全信任测试**：只要测试绿就通过，不看代码。
3. **双层卡口**：机器验收（AST 静态检查 + pytest）+ LLM 审查，**两者都通过才放行**，
   冲突时以机器为准。
4. **人工终审**：所有结果汇总给人，由人决定。

## 决定

选 **方案 3**，并落实为三处硬约束：

1. 每轮审查前先跑 `core/verify.py`（AST 检查 + 在干净工作区跑 pytest），
   结果作为证据写进审查 Agent 的 Prompt；
2. `ReviewerAgent` 里加保险：自动验收未过而模型给了 `approved`，强制改成不通过，
   并追加一条 `R-AUTO` 问题；
3. 编排器再兜一层：`approved and machine_ok` 才迁移到 `APPROVED`，
   冲突时写一条 DEC（`审查通过但自动验收未过，强制驳回`）。

## 理由

- 测试与 AST 检查是**可复现的客观事实**，LLM 结论不可复现；验收看的是测试绿。
- 把证据放进 Prompt 显著降低「顺着代码说好话」的概率：审查 Agent 看到
  `8 failed` 时很难再判通过。
- 三处冗余不是重复：Prompt 层减少错误结论，Agent 层修正模型，编排器层守住终态。
  任何一层被绕过，结论仍然安全。

## 代价与后果

- 每轮多跑一次 pytest（约 0.2s），需要测试文件与干净工作区。
- 静态检查是启发式的（如「get/put 内不得有 for 循环」），可能误报；
  因此只把「锁」「签名」「类存在」「语法」设为硬性，其他降级为警告，
  避免因为风格问题把好代码挡在门外。
- 测试本身可能不全：机器通过 ≠ 实现正确。这是这套设计的能力边界，
  只能在 README 里如实说明（测试覆盖 25 个用例，覆盖 6 条验收项）。

## 复核条件

若测试集出现不稳定（flaky）用例，需要先把测试修稳，否则卡口会误杀正确实现。
